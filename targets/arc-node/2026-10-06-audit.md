# Arc Node Audit Log - 2026-10-06

## Target

- Repository: https://github.com/circlefin/arc-node
- Local checkout: `~/bountyprograms/arc-node`
- Audited revision: `6e76402`
- Commit: `fix(consensus): open the store only after the execution engine is reachable (#467)`
- Date: 2026-10-06
- Research goal: identify a genuine, remotely exploitable vulnerability suitable for responsible disclosure. No speculative issue is treated as a finding without an attacker path and security impact.

## Audit approach

The review focused on consensus synchronization, proposal and vote handling, RPC/admin surfaces, EVM/execution boundaries, transaction-pool behavior, precompiles, and panic/unwrap paths.

For each lead, the target was to establish:

`attacker-controlled input -> reachable code path -> unsafe/security-relevant state change -> concrete impact`

## Findings status

**No confirmed vulnerability identified in this session.**

Several potentially interesting code paths were investigated and closed after tracing their surrounding validation or invariant guarantees.

---

## 1. RPC sync certificate / block binding

### Area

`crates/malachite-app/src/rpc_sync/client.rs`

### What was checked

The RPC sync client requests commit certificates and execution blocks for a height range. The review checked whether a malicious or inconsistent RPC response could be reordered or mismatched across heights.

### Validation observed

The client verifies response counts, requested heights, block numbers, and the recomputed block-header hash before constructing the synced value.

### Result

**Closed.**

No practical batch-response substitution or reordering path was established.

---

## 2. RPC sync network actor

### Area

`crates/malachite-app/src/rpc_sync/network.rs`

### What was checked

Reviewed how configured sync endpoints are queried and how returned certificates and payload bytes are passed into consensus processing.

### Result

**Closed.**

The reviewed path did not expose a new unauthenticated attacker-controlled primitive that bypasses downstream validation.

---

## 3. WebSocket sync tip handling

### Area

`crates/malachite-app/src/rpc_sync/ws_subscription.rs`

### What was checked

The configured WebSocket endpoint reports block heights through `newHeads`. The question was whether arbitrary heights could directly manipulate consensus state.

### Result

**Closed.**

The endpoint is configured/trusted infrastructure, and the reviewed behavior appeared limited to tip information / possible denial-of-service effects rather than consensus forgery.

---

## 4. Synced proposal / execution-payload validation

### Area

`crates/malachite-app/src/handlers/process_synced_value.rs`

### What was checked

Reviewed whether a synced execution payload could enter storage or execution without sufficient validation.

### Validation observed

The handler decodes the payload, constructs a consensus block, establishes block validity, checks height and parent-hash relationships, calls the execution engine, and rejects invalid payloads.

### Result

**Closed.**

No bypass of the reviewed validation chain was established.

---

## 5. Commit certificate verification

### Area

Pinned Malachite dependency at:

`72143f6c99a98452b587e1c392bdb80944eb2232`

### What was checked

Investigated whether an attacker could forge or inject an invalid extended commit certificate during synchronization.

### Critical validation observed

Malachite's sync path explicitly invokes extended commit-certificate verification before applying the certificate. The verification path covers signatures, validator set/quorum requirements, duplicate votes, vote types, and vote-extension policy.

### Result

**Closed.**

Certificate-forgery through the reviewed sync path is not a valid finding.

## 6. Commit certificate HTTP decoding

### Area

`crates/types/src/commit_http.rs`

### What was checked

Reviewed certificate field parsing, including height, round, block hash, and signature bytes.

### Validation observed

- Signature byte length is constrained to 64 bytes.
- Round parsing must fit the expected `u32` range.
- Conversion itself is not the final trust boundary because certificate verification occurs later.

### Result

**Closed.**

No independently reportable flaw found in the parsing layer.

## 7. RPC admin persistent-peer endpoint

### Areas

- `crates/malachite-app/src/rpc/routes.rs`
- `crates/malachite-app/src/rpc/handlers.rs`
- `crates/malachite-app/src/main.rs`

### What was checked

Reviewed the `POST /persistent-peers` and `DELETE /persistent-peers` admin routes, their exposure, and peer-address validation.

### Observation

The handler accepts a Multiaddr and forwards it to the networking layer. A commented validation block references a future change requiring `/p2p/<peer_id>`.

### Result

**Not treated as a new vulnerability.**

The admin router is only mounted when admin functionality is enabled, and the reviewed code did not provide enough evidence of a default remotely exploitable security issue. This was also compared against existing project tracking around persistent-peer `/p2p` validation.

---

## 8. Proposer selector invariant

### Area

`crates/types/src/proposer.rs`

### What was checked

Investigated the `expect("proposer_index is valid")` path for a potential panic triggered by network-controlled height or round values.

### Reason the panic is not exploitable from this path

The selected index is calculated as:

`(height - 1 + round) % validator_set.len()`

after asserting a non-empty validator set and a non-negative, non-nil round. The modulo operation guarantees the resulting index is below `validator_set.len()`.

### Result

**Closed.**

The `expect` is enforcing an internal invariant rather than trusting an attacker-controlled index.

---

## 9. Pending future proposal storage

### Areas

- `crates/malachite-app/src/handlers/received_proposal_part.rs`
- `crates/consensus-db/src/store.rs`
- `crates/malachite-app/src/handlers/consensus_ready.rs`

### What was checked

Future-height and future-round proposal parts are stored before normal current-round proposer/signature validation. The question was whether this could be abused for unbounded storage growth or replacement of valid pending proposals.

### Validation observed

The pending-proposal store applies a bounded future-height window and a global capacity limit. When the capacity is full, further proposals are rejected. Existing entries are not displaced by the overflow attempt, and tests cover the capacity boundary.

### Result

**Closed.**

The reviewed implementation has explicit storage bounds.

---

## 10. Precompile macro input parsing

### Area

`crates/precompiles/src/macros.rs`

### What was checked

Investigated:

`input_bytes[0..4].try_into().unwrap()`

as a possible panic from short attacker-controlled calldata.

### Guard observed

The macro returns a controlled revert when the input is shorter than four bytes. The four-byte conversion occurs only after that guard.

### Result

**Closed.**

The `unwrap` is protected by the preceding length check.

---

## 11. Height overflow / protobuf conversion

### Areas

- `crates/types/src/proposal.rs`
- `crates/types/src/vote.rs`
- proposal-part handling and pending-storage paths

### What was checked

`Height::from_proto(proto.height)` accepts the protobuf `u64` value without a narrow range check. The question was whether `u64::MAX` or another malicious height could become consensus state or cause arithmetic failure.

### Result

**Closed.**

The reviewed network-input paths distinguish past/current/future heights. Future proposals are constrained to a bounded pending window rather than becoming the node's current consensus height. No attacker-controlled height-overflow path into consensus state was established.

---

## 12. Execution payload gas-overflow expectations

### Area

`crates/evm/src/evm.rs`

### What was checked

Production code contains checked additions followed by `expect` in subcall gas accounting:

- `init_subcall_gas_overhead + child_gas.total_gas_spent()`
- resulting value + `completion_gas`

The review asked whether an attacker-controlled transaction could drive the arithmetic above `u64::MAX` and remotely terminate the node.

### Result

**Not confirmed / closed for this session.**

The arithmetic is clearly production code, but the current review did not establish a concrete attacker-controlled route capable of exceeding the relevant gas constraints. This should only become a vulnerability candidate after a reproducible transaction-level trigger is found.

## Session conclusion

This session did not produce a confirmed HackerOne-quality vulnerability.

The most useful outcome was reducing several tempting leads to known-safe or insufficiently demonstrated paths. In particular, certificate-forgery, proposal-height overflow, pending-proposal storage exhaustion, precompile short-input panic, and proposer-index panic were not supported after tracing the surrounding code.

### Next research focus

Resume from the **EVM <-> consensus boundary**, with emphasis on:

1. Attacker-controlled integer conversions between EVM types and consensus/execution types.
2. Block number and timestamp assumptions.
3. Transaction and block gas limits versus internal accounting.
4. Execution results that can create disagreement between execution and consensus.
5. Transaction-pool validation differences that could cause resource exhaustion or inconsistent state.
6. Precompile call/subcall state rollback and authorization semantics.
7. RPC/network behaviors that can be turned into concrete remote DoS or state-manipulation primitives.

### Standard for a future finding

Do not promote a lead to a report until the chain is demonstrated:

`attacker sends X -> code reaches Y -> node does Z -> measurable security impact`

Potential impact should be concrete, such as consensus failure, chain halt, remotely triggered node crash, unauthorized state transition, or a practical remote denial of service.

## Research hygiene

This document records **closed leads as research notes, not vulnerabilities**. Keep unreported exploit details private until the issue is reproduced and disclosure is appropriate.
